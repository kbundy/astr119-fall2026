  - It stores only three numbers (P_a, P_b, P_k) however large n gets.

  What the "slow way" looks like, for comparison. The docstring warns against
  having legpoly(n, x) call legpoly(n-1, x) and legpoly(n-2, x). Each of those
  calls two more, and so on, so the number of calls roughly doubles with each
  step up in n. For n = 3501 that would never finish. Your loop does about 3500
  steps.

  Ways to speed it up in practice:

  1. A tidier loop. if k == n is checked on every pass, but it's only true once.
     You could shift every time and set y = P_a after the loop ends. With the
     right starting values, the n == 1 case even handles itself. It's a small
     gain, mostly in readability.
  2. Use a library. scipy.special.eval_legendre(n, x) uses essentially the same
     recurrence, but written in compiled C, so it runs much faster than a Python
     loop. It also accepts a whole array of x values at once. That matters when
     you're plotting Pₙ at 1000 points. Your version needs a Python loop over
     x, and its assert on x would fail for an array anyway. scipy is already in
     your environment.
  3. Very large n. There are approximate formulas for Pₙ when n is huge that
     skip the loop entirely. You won't need them in this course.

  One "faster-looking" method that's actually worse. Pₙ has an explicit formula
  as a sum of powers of x with binomial coefficients. For large n those terms
  become enormous and alternate in sign, so they nearly cancel. With
  floating-point numbers you lose almost every correct digit. The recurrence
  doesn't have that problem, which is one reason it's the standard method.

  To check this yourself, compare your function with scipy:

  >>> from legendre import legpoly
  >>> from scipy.special import eval_legendre
  >>> legpoly(50, 0.3), eval_legendre(50, 0.3)

  Before running it, how closely do you expect the two to agree? Exactly, or to
  about how many digits?
